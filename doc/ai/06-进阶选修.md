# 六、进阶选修

本文是学习路线的阶段五之后的进阶主题（按需选修，建议在主线完成后按兴趣挑 1–2 项深入）。


## 一、长期记忆（Long-term Memory）

### 1.1 记忆类型

| 类型     | 存储              | 内容                                   | 生命周期          |
|----------|-------------------|----------------------------------------|-------------------|
| 工作记忆 | 上下文窗口        | 当前对话、工具结果                     | 会话内，需压缩    |
| 情景记忆 | 向量库/结构化存储 | 过往会话的关键事实与决定               | 跨会话，可检索    |
| 语义记忆 | 知识库            | 抽取出的稳定事实（用户偏好、环境信息） | 长期，需更新/去重 |
| 程序记忆 | 提示词/配置       | 学到的操作流程与规范                   | 长期，版本化      |

### 1.2 工程要点

- **写入策略**：会话结束/定期触发"记忆抽取"（用 LLM 从对话中提炼事实），不是全量存对话；
- **检索策略**：embedding 相似度 + 时间衰减 + 重要性评分；只注入相关片段，控制 token；
- **更新与冲突**：事实会过期（"用户在 A 部门"→ 调岗），需要版本/有效期字段与合并策略；
- **隐私与权限**：记忆按租户/用户隔离，支持删除（合规要求）。

**参考**：Generative Agents（斯坦福小镇）的 memory stream + 反思机制是经典设计。


## 二、多智能体协作（Multi-Agent）

### 2.1 模式

| 模式           | 结构                         | 适用                                         |
|----------------|------------------------------|----------------------------------------------|
| Supervisor     | 主控分派 + 汇总              | 任务可拆、需统一把关（最常用）               |
| Handoff        | 链式移交（A 做完交给 B）     | 流程化分工（客服→技术→工单）                 |
| Swarm/去中心化 | 平等协作、共享状态           | 研究性质，生产少用                           |
| 子 Agent 隔离  | 子任务独立上下文，只回传结论 | **上下文隔离是最大价值**：避免长任务互相污染 |

### 2.2 决策与陷阱

- **先问"单 Agent + 好的上下文工程能不能解决"**——多智能体带来协调成本与错误放大；
- 拆分标准：任务边界清晰、上下文互不依赖、可独立评估；
- Supervisor 的汇总环节是质量瓶颈，要有评估；
- 参考 04 册资源：Anthropic《How we built our multi-agent research system》。


## 三、Coding Agent 原理

Coding Agent 是当前最成熟的 Agent 形态，其原理可直接反哺通用 Agent 设计：

- **CodeAct 范式**：模型不只输出工具调用 JSON，而是直接写**可执行代码**作为动作（执行结果含 stdout/报错回填）——表达力远超固定工具集；
- **SWE-agent / SWE-bench**：论文与基准，理解"文件编辑器 + shell + 测试反馈"如何构成 Agent-计算机接口（ACI）；
- **工具设计的启示**：Coding Agent 的编辑工具带"搜索/精确替换/预览"，正是把**工具描述与参数设计当作产品来做**的范例；
- **实践**：把 OpenCode/Claude Code 这类真实工具当解剖对象——观察它的系统提示、工具清单、上下文压缩、子 Agent 派生行为。

**参考**：论文《Executable Code Actions Yield Better LLM Agents》（CodeAct）、SWE-agent 论文、SWE-bench 榜单。


## 四、微调（Fine-tuning）的适用边界

**默认不微调**。判断顺序：

1. **提示词/示例优化**能解决吗？（成本最低）
2. **RAG / 工具**能解决吗？（知识与能力外置）
3. **上下文工程**能解决吗？（few-shot 示例放窗口）
4. 以上都解决不了的**稳定、高频、格式化**需求（如特定领域术语、固定输出风格、小模型降本），才考虑微调。

微调入门认知：
- **LoRA/QLoRA**：低秩适配，单卡可训，是主流低成本方案；
- 微调擅长"**行为与格式**"，不擅长"**注入新知识**"（新知识请用 RAG）；
- 评测：微调前后必须跑同一 golden set，防止"风格像了、正确率掉了"。

**参考**：HuggingFace PEFT 文档、OpenAI/Anthropic 关于 when to fine-tune 的官方指南。


## 五、其他可关注方向

- **多模态 Agent**：截图理解（computer use）、图表解析、语音输入；
- **Agent 评测基准**：GAIA、AgentBench、SWE-bench 等，了解当前能力边界；
- **推理模型（Reasoning Models）**：o 系列/R1 类模型的思考过程与成本权衡——何时值得为"思考"付费；
- **Workflow 引擎结合**：Flowable/Zeebe（你熟悉的流程引擎）与 Agent 混合——**确定性流程走引擎，弹性判断走 Agent**，这是企业架构的现实答案。
