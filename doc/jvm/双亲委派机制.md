### 什么是双亲委派机制？

当一个类加载器收到类加载请求时，不会自己先去加载，而是把请求**向上委派给父类加载器**执行，每一层都是如此；只有当父类加载器无法完成加载（在其搜索范围内找不到该类）时，子类加载器才会自己尝试加载。

> 向上委派查找，父类加载器优先；向下只负责返回已加载的结果，真正找不到时才由下层加载。

#### 类加载器的层次结构与继承关系

**委派/层级关系（自上而下）：**

```
BootstrapClassLoader（启动类加载器，C++ 实现，加载 rt.jar 等核心类库）
        ↑ parent
ExtensionClassLoader（扩展类加载器，JDK9+ 为 PlatformClassLoader，加载 ext 目录）
        ↑ parent
ApplicationClassLoader（应用程序类加载器/系统类加载器，加载 classpath）
```

**Java 继承关系（自下而上）：**

```
AppClassLoader、ExtClassLoader ==> URLClassLoader ==> SecureClassLoader ==> ClassLoader
```

注意区分：
- **委派关系**（parent 指针）是类加载器实例之间的组合关系；
- **继承关系**是 `ClassLoader` 抽象类的 Java 类层次；
- `BootstrapClassLoader` 由 HotSpot 用 C++ 实现，**不在** Java 继承体系中，`Ext/AppClassLoader` 的 `parent` 为 `null` 时表示委派给它。


#### 双亲委派的工作流程（loadClass 源码）

`ClassLoader#loadClass` 是委派逻辑的核心：

```java
protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException
{
    synchronized (getClassLoadingLock(name)) {
        // 1. 检查该类是否已经被加载过
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                // 2. 优先委派给父类加载器加载
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    c = findBootstrapClassOrNull(name); // parent 为 null 委派给启动类加载器
                }
            } catch (ClassNotFoundException e) {
                // 父类加载器加载不到，忽略异常，交给自己加载
            }
            if (c == null) {
                // 3. 父类加载器加载不到，才调用自身的 findClass 加载
                c = findClass(name);
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}
```

流程总结：**查缓存 → 委派父类 → 父类找不到再自己 findClass**。


### 为什么要采用双亲委派机制？

#### 1. 沙箱安全机制，防止核心库被篡改

保证 Java 核心 API（如 `java.lang.String`、`java.lang.Object`）永远由顶层的 `BootstrapClassLoader` 加载。

**场景**：假如自己在项目里写了一个 `java.lang.String` 并塞进 classpath：
- 若没有双亲委派，AppClassLoader 可能加载到用户伪造的 `String`，核心类库被替换，程序行为不可预期；
- 有了双亲委派，请求会一路委派到 BootstrapClassLoader，由它加载 JDK 自带的 `rt.jar` 中的 `String`，用户同名类永远不会被加载，从而保护核心 API 不被覆盖、保证核心类的类型安全。

这也是 `java.*` 开头的包在自定义类加载器中通常会抛 `SecurityException`/`ClassNotFoundException` 的原因——不允许应用程序扩展或覆盖核心包。

#### 2. 避免类的重复加载

类的唯一性由「**全限定名 + 加载它的类加载器**」共同决定。

**场景**：项目中多个 jar 都依赖了 `commons-lang3`，或多个插件都用到同一个工具类：
- 若每个类加载器各自为政，同一个 `org.apache.commons.lang3.StringUtils` 可能被加载多次，在方法区中出现多份类型信息，既浪费元空间，又会导致 `instanceof`、强制类型转换等跨加载器判断失败；
- 双亲委派下，只要父类加载器已经加载过该类，直接复用其 `Class` 对象，保证同一个类在 JVM 中的唯一性，也保证了类型比较的正确性。

#### 3. 层次结构中的职责分层（补充）

- 启动类加载器：JVM 核心类库，权限最高；
- 扩展类加载器：Java 平台扩展功能；
- 应用类加载器：应用程序自身代码。

委派模型让「越核心的类越由上层加载」，形成天然的权限与职责边界。


### 实际场景：哪些地方会打破双亲委派？

双亲委派并非不可违反，以下实际工程场景都主动打破了它：

#### 场景 1：SPI 机制（JDBC）—— 父加载器加载不到子加载器的类

以 JDBC 为例：
- `java.sql.DriverManager`、`java.sql.Connection` 等接口由 **BootstrapClassLoader** 加载（属于 JDK 核心 API）；
- 具体实现（如 MySQL 驱动 `com.mysql.cj.jdbc.Driver`）在应用 classpath 中，只能由 **AppClassLoader** 加载；
- 双亲委派下 Bootstrap 永远"向下看不见"应用层的实现类，若严格委派则无法完成驱动加载。

**解决方式**：JDBC 使用**线程上下文类加载器（Thread Context ClassLoader，默认是 AppClassLoader）**，由 `DriverManager` 反调应用层类加载器去加载驱动实现，形成"父加载器请求子加载器"的**逆向委派**。

> 同类场景：JNDI、Dubbo 等 SPI 扩展也都依赖 TCCL。

#### 场景 2：Tomcat —— 每个 Web 应用独立隔离

Tomcat 中每个 webapp 都有各自的 `WebappClassLoader`，加载顺序与双亲委派相反：

```
先加载当前 webapp 的 /WEB-INF/classes 和 /WEB-INF/lib
       ↓ 找不到
再委派给 CommonClassLoader（Tomcat 公共类）
       ↓ 找不到
最后才交给 JVM 的系统类加载器
```

**原因（为什么不用标准双亲委派）**：
1. **应用间隔离**：两个 war 包可以依赖同一个 jar 的**不同版本**（如 app1 用 spring 5、app2 用 spring 6），若先委派给公共/系统加载器，只能加载一份，版本会冲突；
2. **应用内优先**：webapp 自己的类优先于容器公共类，支持热部署、应用独立卸载/卸载。

> 对应面试题：「Tomcat 中为什么要使用自定义类加载器」——核心答案就是**同类隔离、版本隔离、支持热部署**。

#### 场景 3：热部署 / OSGi —— 网状而非树状

- 传统双亲委派是**树状**结构；
- OSGi Bundle 之间是**网状**依赖：bundle 加载类时先查本 bundle，再查 Import-Package 导出的 bundle，不完全向上委派；
- IDE/框架的热部署（如 JRebel、devtools）也常通过自定义类加载器丢弃旧 Class、重新加载变更类来实现，天然绕过"已加载则直接复用"的委派缓存。

#### 场景 4：Spring Boot 可执行 fat jar

Spring Boot fat jar 中依赖都在 `BOOT-INF/lib/` 下，不在系统 classpath 中，JVM 默认类加载器找不到，因此使用自定义的 `LaunchedURLClassLoader` 加载 `BOOT-INF/classes` 与 `BOOT-INF/lib` 中的类。


### 如何自己实现一个打破双亲委派的 ClassLoader？

核心：**重写 `loadClass()` 而不是 `findClass()`**（`findClass` 只负责真正读字节码，`loadClass` 才是委派入口）。

```java
public class NoParentClassLoader extends ClassLoader {
    @Override
    public Class<?> loadClass(String name) throws ClassNotFoundException {
        // 1. 优先自己加载（打破“父优先”）
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            if (!name.startsWith("java.")) { // 核心类仍交给父加载器，保证安全
                c = findClass(name);
            }
            if (c == null) {
                c = super.loadClass(name, false); // 兜底走双亲委派
            }
        }
        return c;
    }
}
```

要点：
- 只对**业务类**改为"自己优先"，`java.*` 等核心包仍必须委派，否则会破坏沙箱；
- Tomcat、OSGi、SPI 上下文加载器本质上都是这类变体。


### JDK 9+ 模块化（JPMS）后的变化

- `ExtClassLoader` 被 **`PlatformClassLoader`** 取代（扩展目录机制废弃，改为模块路径）；
- 启动类加载器仍然负责 `java.base` 等核心模块；
- 模块系统通过 `module-info.java` 的 `requires`、`exports` 在**编译期与运行期**提供更强封装，是双亲委派沙箱安全的进一步补充，但双亲委派本身依然存在。


### 面试答法速记

1. **定义**：先委派父加载器，父加载器加载不了自己才加载；
2. **层次**：Bootstrap → Ext(Platform) → App，配合 `loadClass` 源码三步：查缓存、委派父、自己 findClass；
3. **为什么**：① 沙箱安全，防止核心类被篡改/覆盖；② 避免重复加载，保证类唯一性；③ 职责分层；
4. **打破的场景**：SPI/JDBC（TCCL 逆向委派）、Tomcat WebappClassLoader（应用隔离、版本冲突）、OSGi/热部署（网状加载）、Spring Boot fat jar（LaunchedURLClassLoader）；
5. **怎么打破**：重写 `loadClass`，业务类自己优先，核心类仍委派。
