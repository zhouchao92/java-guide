#### synchronized 的锁升级过程？

锁状态记录在对象头 Mark Word 中（详见 [对象头 Markword](/doc/jvm/对象头%20Markword.md)），升级目的是在竞争由弱变强时逐步降低同步开销：

**无锁 → 偏向锁 → 轻量级锁 → 重量级锁**（单向升级，重量级锁不会自动降级）

| 状态     | 触发时机                         | 实现方式                                                                          | 开销               |
|----------|----------------------------------|-----------------------------------------------------------------------------------|--------------------|
| 无锁     | 对象刚创建，尚无同步操作         | Mark Word 记录 hashcode 等                                                        | —                  |
| 偏向锁   | 第一个线程进入同步块             | CAS 将 Mark Word 偏向该线程并记录线程 ID，同线程再次进入只需比较 ID，无 CAS       | 最小               |
| 轻量级锁 | 出现第二个线程竞争，但竞争不激烈 | 线程栈帧中复制锁记录，CAS 替换 Mark Word 指向栈帧；失败则自旋重试                 | 较小（用户态自旋） |
| 重量级锁 | 自旋超过一定次数，或多个线程竞争 | ObjectMonitor（monitorenter/monitorexit），未抢到锁的线程阻塞挂起，涉及内核态切换 | 最大               |

详细过程：

1. **无锁 → 偏向锁**：第一个线程进入同步块时，CAS 将 Mark Word 偏向该线程并记录线程 ID；此后同线程进入/退出只需比较 ID（偏向锁撤销前不执行 CAS）。注意：对象已生成 hashcode 或被 GC 标注时不能偏向
2. **偏向锁的撤销**（不同线程竞争时才撤销，且须在安全点进行）：
   - 偏向线程**未在**执行同步代码：直接撤销为无锁状态，再参与锁竞争
   - 偏向线程**仍在**执行同步代码：到达安全点后撤销，结果可能是——置为无锁、重偏向给新线程、或升级为轻量级锁
3. **轻量级锁 → 重量级锁**：抢锁失败则 CAS 自旋重试，当自旋超过一定次数（早期 HotSpot 固定 10 次，JDK 6+ 为自适应自旋），或存在超过 2 个线程竞争时，升级为重量级锁，等待线程进入阻塞队列挂起

补充：

- **升级是单向的**：轻量级/重量级锁不会自动降级（避免刚升级又被抢、反复转换的开销）
- **JDK 15 起偏向锁默认关闭**（JEP 374）：现代多核 CPU 上撤销偏向的成本常高于收益，可通过 `-XX:+UseBiasedLocking` 打开
- **各状态的本质**：偏向锁适合"几乎无竞争"；轻量级锁适合"短暂竞争，自旋可等到"；重量级锁适合"竞争激烈，阻塞比空转划算"


#### synchronized 和 Lock 的区别？

|          | synchronized                                                | Lock（以 ReentrantLock 为代表）                                                |
|----------|-------------------------------------------------------------|--------------------------------------------------------------------------------|
| 存在层次 | 关键字，JVM 层（字节码 monitorenter/monitorexit）           | Java 接口，API 层                                                              |
| 锁的获取 | 阻塞式等待，无法尝试获取、无法设置超时、不可中断            | 可 `tryLock()` 尝试获取、`tryLock(timeout)` 超时、`lockInterruptibly()` 可中断 |
| 锁的释放 | 1. 执行完同步代码自动释放；2. 抛异常时 JVM 也会释放         | 必须在 finally 中手动 `unlock()`，否则造成死锁                                 |
| 锁类型   | 可重入、非公平、独占                                        | 可重入、可中断、可公平/非公平（默认非公平）、独占，另有 ReadWriteLock 共享读锁 |
| 条件协作 | `wait`/`notify`/`notifyAll`，对象上单一等待队列             | 可绑定多个 `Condition`，支持精确唤醒                                           |
| 性能     | JDK 6 优化后，无竞争场景与 Lock 基本相当                    | 适合功能要求多、大量同步的场景                                                 |
| 底层原理 | Monitor + 锁升级（偏向 → 轻量 → 重量），轻量级阶段 CAS 自旋 | AQS：volatile state + CLH 等待队列，CAS + park/unpark                          |

如何选择：

- 默认优先 `synchronized`：写法简单，自动释放锁，不会忘记 unlock
- 需要尝试获取/超时获取、可中断等待、公平锁、多条件精确唤醒时用 `ReentrantLock`
