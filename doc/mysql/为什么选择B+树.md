#### 为什么选择B+树？

MySQL（InnoDB）选择 B+树，本质是因为**磁盘 IO 是数据库的性能瓶颈**：B+树矮胖（扇出大、树高小），一次查询只需极少的磁盘 IO；非叶子节点不存数据，单页能容纳更多 key，树更矮；叶子节点用双向链表相连，天然支持范围查询、排序和分页。

---

#### 前置认知：为什么"树高"决定性能

- InnoDB 中数据以**页（Page）为单位**读写，默认 **16KB**
- 访问索引树的一个节点 = 把该页从磁盘加载进 Buffer Pool = **一次磁盘随机 IO**
- 查找一次数据的 IO 次数 ≈ **树的高度**，所以树越矮，IO 次数越少

**树高对比估算**（1000 万行数据，主键 BIGINT 8 字节）：

| 数据结构        | 每个节点可存指针/数据                           | 估算树高 | 磁盘 IO 次数 |
|-----------------|-------------------------------------------------|----------|--------------|
| 二叉树 / 红黑树 | 1 个 key + 2 个指针                             | ≈ 24 层  | 24 次        |
| B+树（InnoDB）  | 一个 16KB 页 ≈ 1170 个指针（主键 8B + 页号 6B） | ≈ 3 层   | 3 次         |

> 3 层 B+树可存约 `1170 × 1170 × 16 ≈ 2100 万` 行索引，绝大多数表**只需 2~3 层**。

---

#### 为什么不用红黑树？

红黑树是**二叉**结构，本质是内存数据结构，不适合磁盘存储：

1. **树太高**：每个节点只有 2 个分支，1000 万数据需要约 24 层，最坏 24 次磁盘 IO，完全不可接受
2. **节点太小、IO 利用率低**：磁盘一次读 16KB，红黑树一个节点只装一个 key，读 16KB 却只用几十字节，浪费严重
3. **非顺序存储**：数据散落在不同磁盘位置，读取时随机 IO 多
4. **场景错配**：红黑树优势在内存中的频繁插入/删除（如 `HashMap` 树化、`epoll` 的 fd 管理），而数据库是**读多、写少、以 IO 为主**的场景

> 面试加分：不是红黑树不好，而是**磁盘场景需要"多路"而不是"二叉"**——降低树高只能靠增大扇出，这就是 B 树家族的由来。

#### B 树和 B+树的区别

| 对比项       | B 树                                                       | B+树                                           |
|--------------|------------------------------------------------------------|------------------------------------------------|
| 数据存储位置 | 非叶子节点和叶子节点**都存数据**                           | 数据**只存叶子节点**，非叶子节点只存 key       |
| 叶子节点     | 互不相连                                                   | 用**双向链表**串联，有序                       |
| 关键字数量   | 等于数据量                                                 | 等于索引数量（与数据量一致时同上）             |
| 扇出 / 树高  | 节点要留空间放数据，扇出小、树高更大                       | 节点纯索引，扇出大、**树更矮**                 |
| 查询效率     | **不稳定**：可能在非叶子节点命中（快），也可能到叶子（慢） | **稳定**：任何查询都走到叶子节点，路径长度一致 |
| 范围查询     | 需回溯遍历（中序遍历整棵树）                               | 叶子链表**顺序扫描**即可                       |
| 缓存友好度   | 差：数据混在节点中，一页里有效 key 变少                    | 好：一页全是 key，能缓存更多索引项             |

#### 为什么 B+树更适合作为 MySQL 索引？（好处）

1. **更低的树高 → 更少的磁盘 IO**
   非叶子节点不存数据，16KB 的页能塞下上千个 key，扇出极大，树高通常只有 2~3 层。

2. **查询性能稳定**
   所有查询都必须走到叶子节点，IO 次数固定，便于做性能预估和优化。

3. **范围查询、排序、分页天然高效**（对比 B 树的核心优势）
   - `WHERE age BETWEEN 20 AND 30`、`ORDER BY`、`LIMIT` 只需定位起点，然后沿叶子链表顺序读
   - B 树要中序遍历回溯，产生大量随机 IO
   - InnoDB 叶子链表是**双向**的，`ORDER BY ... DESC` 也能反向扫描

4. **缓存/预读利用率高**
   非叶子节点全是索引 key，Buffer Pool 同样内存能缓存更多索引项，命中率更高；顺序读也符合磁盘预读原理。

5. **文件体积更小**
   数据只存一份在叶子节点（聚簇索引），非叶子节点不冗余存储数据。

#### 追问扩展

**Q1：为什么不用 Hash 索引？**
- Hash 只支持等值查询，**不支持范围、排序、最左前缀、分组**
- 存在哈希冲突，需要额外处理；而 B+树本身就是有序的
- （补充：InnoDB 的自适应哈希索引 AHI 是对热点页的加速，不是替代）

**Q2：为什么不用 B*树？**
- B*树非叶子节点利用率要求 2/3（B树/B+树是 1/2），理论上树更矮
- 但节点满时先向兄弟"借位"、再分裂，**分裂算法复杂、并发控制代价高**
- MySQL 未采用；收益有限，工程复杂度不划算

**Q3：和 LSM-tree 比呢？**（亮点题）
- B+树：**读优化**，读快、写需要随机更新页（靠 Buffer Pool + WAL 改善）
- LSM-tree：**写优化**，顺序写 WAL + 后台 compaction，适合写密集场景（RocksDB、HBase）
- MySQL InnoDB 面向通用 OLTP，读写均衡，选 B+树；`redolog` 本质就是借鉴了顺序写的思想

**Q4：为什么叶子节点要链表相连，非叶子节点不用？**
- 非叶子节点只用于"导航"，不需要横向遍历；叶子节点承载全部数据，链表让范围扫描变成顺序 IO

#### 面试话术

> **（瓶颈）** 数据库数据量大，索引必须放磁盘，而磁盘随机 IO 很慢，所以核心目标是**减少 IO 次数、降低树高**。
>
> **（排除红黑树）** 红黑树是二叉结构，1000 万数据要 24 层，IO 次数太多，且节点只装一个 key，16KB 的页严重浪费。
>
> **（B树 vs B+树）** B树的节点里混存了数据，导致扇出小、树更高；而且查询可能命中非叶子节点，效率不稳定，范围查询还要中序遍历回溯。
>
> **（B+树优势）** B+树把数据全放叶子节点，非叶子节点只存 key，一个 16KB 页能放上千个指针，扇出大，树高只有 2~3 层，IO 少且稳定；叶子节点用双向链表串联，范围查询、排序、分页都是顺序 IO，非常快。
>
> **（总结）** 所以 B+树是磁盘存储下"低 IO + 支持范围查询"的最优权衡。
